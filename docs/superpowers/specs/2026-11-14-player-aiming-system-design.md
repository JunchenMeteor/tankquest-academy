# 玩家瞄准系统拆分设计

## 背景与目标

`battle-view.ts` 同时处理驾驶、瞄准、敌人、碰撞、战斗和渲染，近期多次出现地形、炮塔、炮口和开火条件相互影响的回归。真实 RTX 2070 三关基线约为 60 FPS，当前首要问题是复杂度和可验证性，而不是帧率不足。

本阶段只做方案 A 的第一步：把玩家瞄准从中央视图拆成独立控制器，保持现有玩家体验、公开 API、60 Hz 固定步进和帧执行顺序。后续敌人、战斗和渲染同步拆分不在本 PR 内。

## 已确认约束

- 保留 `createBattleView()` 的签名和 `Battle3DHandle` 契约。
- 保留 Pointer Lock、虚拟准心、右键环视、手动炮塔控制和输入清理。
- 保留 `RuntimeState.turret` 作为炮塔逻辑角，保留 `gunPitch` 作为炮管局部角。
- 保留真实炮口闭环：水平方向比较实际炮口轴向与目标方向，俯仰在炮管父节点局部空间从炮口解算。
- 保留车体俯仰/横滚补偿、炮管局部限位和炮塔/俯仰转速差异。
- 未对齐只改变准心颜色；玩家开火只受弹药、冷却和输入请求约束。
- 炮弹从当前真实炮口沿真实世界方向发射，不重新施加世界俯角限幅。
- 不修改后端配置、题库、奖励、升级、敌人 AI、地图和物理模型。

## 架构原则

按用户行为和战斗职责划分模块，不按视觉场景机械拆文件。后续边界依次为玩家瞄准、玩家驾驶、敌人战术、战斗结算、地形接触和渲染同步；每个模块必须能独立描述输入、输出和副作用。

控制器在每局战斗创建时由工厂函数组装，并随视图释放，不使用全局单例。只对稳定契约做封装，Three.js 资源仍由场景统一管理。工厂只负责组合依赖，不额外制造继承层、服务定位器或共享状态容器。

## 方案

新增 `player-aim-controller.ts`，由它管理玩家瞄准的两阶段过程。`battle-view.ts` 仍负责生命周期、场景对象和其他系统，不在控制器中注册 DOM 监听器，也不创建或销毁 Three.js 场景资源。

控制器只拥有以下内部状态：

- 当前目标点 `aimPoint`。
- 当前炮管局部角 `gunPitch`。
- 可复用的向量计算对象，避免每个阶段重复分配。

炮塔逻辑角继续存放在 `RuntimeState`，准心和 Pointer Lock 状态继续由现有输入层管理，避免形成第二份隐式状态。

### 控制阶段

输入包括：

- 固定步长、当前位置/朝向/炮塔角的运行时状态。
- 当前驾驶命令、右键状态、鼠标准心和 Pointer Lock 就绪状态。
- 当前相机、可射线检测的敌人根节点和地面组。
- `getRig(): TankRig` 提供的最新玩家 rig、炮塔转速和炮管俯仰速度。GLB 异步替换 rig 时不得继续引用旧的程序化模型，也不得重置瞄准状态。

控制器执行现有顺序：

1. 根据准心射线求最近敌人或地面目标点，无命中时使用最大射程。
2. 从真实炮口轴向闭环求目标世界炮塔角，并按要求转速逼近。
3. 在炮管父节点局部空间，从炮口位置求目标俯角，并按要求转速和局部限位逼近。
4. 右键环视或手动炮塔命令存在时，沿用现有非引导路径，不擅自增加自动瞄准。
5. 返回新的炮塔逻辑角、炮管局部角、目标点和瞄准偏移。

主循环在同一位置把结果应用到 `RuntimeState` 和 rig，不能同时在控制器与视图中各写一次。

### 地形同步与投影阶段

敌人、撞击和统一地形姿态处理仍由主循环完成。随后控制器读取已经更新的真实炮口世界位置与方向：

- 将炮口轴线按目标距离投影为炮口准心。
- 计算炮口准心与鼠标准心的像素位置和对齐提示。
- 返回真实炮口位置、方向以及开炮所需的瞄准数据。

主循环继续使用 `canFire`/`canPlayerFire` 处理弹药、冷却和输入请求，并从真实炮口生成炮弹。对齐误差不得重新成为玩家开火前置条件。

### 建议接口边界

控制器暴露两个明确阶段，而不是一个同时修改所有状态的大函数：

- `updateControl(frame)`：只计算并返回炮塔、炮管和目标点控制结果。
- `updatePresentation(frame)`：只根据最终世界变换计算准心和真实炮口数据。

接口使用现有 `RuntimeState`、`TankRig`、`Camera`、`Object3D` 和向量类型，不引入新的框架、事件总线或全局单例。错误路径继续使用现有含义：未准备瞄准时不更新引导目标，零长度方向按最大角度误差处理，物理限位之外允许不重合但不阻止开火。

## 帧顺序与副作用

必须保持以下顺序，避免一帧延迟：

1. 玩家驾驶与炮塔手动输入。
2. 玩家瞄准控制阶段并应用结果。
3. 敌人、撞击和统一地形姿态。
4. 玩家瞄准投影阶段。
5. 装填、冷却与玩家开火。
6. 敌人开火、炮弹推进、命中和渲染。

DOM 事件、Pointer Lock、相机模式和 React 状态发布仍由现有外层负责。控制器不直接操作弹药，不生成炮弹，不改变敌人，不处理地图碰撞，也不更新 HUD。

## 迁移步骤

1. 先为控制器两阶段接口建立与当前行为一致的回归测试。
2. 引入控制器并接入玩家路径，删除主循环中对应的重复解算。
3. 保留敌人、战斗、地形、输入和场景生命周期原样，不做顺带优化。
4. 更新 `docs/3d-battle/README.md` 的代码索引和瞄准职责说明。
5. 通过完整门禁后，在 Preview 和生产重复平地、坡地、未重合开火和指针输入验收。

如需回滚，还原本 PR 即可恢复中央视图实现，不涉及数据迁移或其他系统。

## 测试与验收

### 自动测试

- 现有全部测试不得减少或跳过。
- 控制阶段覆盖：目标射线、炮塔转速、局部俯仰、车体姿态、炮口偏移、局部限位、右键和手动炮塔路径。
- 投影阶段覆盖：真实炮口投影、双准心像素位置、对齐提示和零长度方向。
- 开火边界覆盖：未重合可开火、无弹药不可开火、冷却未结束不可开火、真实炮口方向不被二次限幅。
- 执行格式、lint、类型检查、全仓测试、构建和 Web 性能预算。

### 浏览器验收

- 使用高画质真实 GLB，在出生地和坡地检查普通目标稳定后的双准心误差，目标为 0 px 或浮点误差内的等效结果。
- 检查超过物理俯角/方向极限时可以不重合，但仍能开火。
- 在未对齐时点击，确认射击次数增加、弹药减少、炮弹从炮口射出。
- 回归 Pointer Lock、右键环视和 Esc 输入清理。
- Preview 与生产使用同一镜像，各完成两轮对抗性复验。

### 性能验收

沿用真实设备基线记录平均 FPS、P95 帧时间、长任务和画质变化。拆分不得引入持续长任务、异常内存增长或额外画质降级；性能结论必须来自实际采样，不从代码结构推断。

## 后续边界

本 PR 完成后，才分别评估敌人系统、战斗系统和渲染同步拆分。地图升级和 Rapier 接入继续遵守独立设计、独立 PR、独立验收的顺序，不把本阶段扩大为物理重写。
